## 3. P0：立即处理

### OPT-001：明确上报 Token 去留并移除 Git 中的 `.env`

**现状证据**

- 基线检查曾发现 `.gitignore` 已忽略 `.env`，但 `git ls-files .env` 仍能看到该文件，说明它已被提交过；本轮已验证当前 `main` 的 `git ls-files .env` 为空，且可达历史不再包含该路径。
- 文件内存在非默认 `API_TOKEN`；本文档不复述其值。
- `app/config.py:7` 在环境变量缺失时回退到可预测的 `default_token`。
- `API_TOKEN` 经 `app/dependencies.py:verify_token()` 校验 `Authorization: Bearer <token>`，当前只保护 3 个外部写接口：
  - `POST /api/v1/qinglong/report`：写入账号、程序及积分/现金历史。
  - `POST /api/v1/stock-report`：写入商品和库存历史；由于请求代表全量快照，本次未出现的在架商品会被自动标记为下架。
  - `POST /api/v1/upload/image`：向服务器上传目录写文件，并可更新商品本地图片路径。
- 前端 Axios 新流程依赖 HttpOnly UI 会话 Cookie，不会使用 `API_TOKEN`；旧版浏览器只在迁移窗口发送 `X-Access-Key`。它也不是青龙 OpenAPI 临时 token，更不是程序的 `auth_type=token`。因此 `API_TOKEN` 的准确角色仍是“采集脚本到本服务的机器间上报凭据”。
- `scripts/api_template.py` 和库存上报文档要求外部脚本携带该 Bearer 凭据。
- `docker-compose.yml` 当前使用 `5711:5711` 发布端口；没有额外网络限制时，可访问宿主机该端口的客户端就能尝试调用上述接口。

**风险**

- 仓库读权限等价于外部上报接口写权限。
- 基线时即使执行 `git rm --cached .env`，历史提交中的 token 仍可能可见；本轮已重写当前 `main` 可达历史并轮换本机凭据，旧值不再作为当前应用凭据使用。
- 部署漏配环境变量时会静默使用公共默认值。
- 若只删除路由上的 `verify_token` 而没有建立网络边界，上述 3 个接口会变成匿名写接口：攻击者可伪造积分、篡改库存/上下架状态，或持续上传文件占用磁盘。
- UI access protection 是可配置的人机界面访问锁，当前由 router-level dependency 统一执行，不能把它与上报 Bearer 凭据混用。

**当前生产 Docker 环境核对**

- 生产 Compose 默认只启动一个 Uvicorn worker，因此当前进程内失败限流覆盖全部 UI 访问请求，不存在多 worker 间计数分散的问题。
- 本轮测试/工作区已验证的代码和配置尚未迁移到生产 Docker；生产 `.env` 仍需单独核对是否使用随机的 `INGEST_TOKEN`，旧 `API_TOKEN` 只保留为兼容迁移，不建议作为长期配置。
- 生产端口是否需要收窄，应根据青龙和其他调用方的网络位置决定：若只需本机访问可绑定 `127.0.0.1:5711:5711`；若需要局域网访问，则应通过局域网/VPN/防火墙限制来源，而不是直接暴露公网。

**建议方案**

先根据部署边界明确二选一，不能只因为前端没有使用它就直接删除：

1. **保留机器鉴权（当前推荐）**
   - 当 `5711` 可被局域网、公网或任何不完全可信客户端访问时，保留这层鉴权。
   - 将服务端变量重命名为语义更清楚的 `INGEST_TOKEN`；如需平滑升级，可让 `API_TOKEN` 只作为一个版本的弃用兼容项。
   - 删除 `default_token` 回退值；凭据缺失、仍为默认值或强度不足时拒绝启动。
   - 使用 `secrets.compare_digest()` 比较凭据，继续只保护上述 3 个接口，不与 UI 会话或青龙 OpenAPI token 混用。
   - 若图片上传已无调用方，优先下线该接口；否则增加类型、大小和内容校验，必要时为上传能力设置独立权限。

2. **移除应用层上报 Token（仅限已有可信网络边界）**
   - 先把容器端口绑定到 `127.0.0.1:5711:5711`，或确保 VPN、反向代理鉴权、IP allowlist、mTLS 等边界已生效，并阻止绕过代理直连宿主机端口。
   - 验证不可信网络无法直接访问 3 个写接口后，再移除 `verify_token`、`API_TOKEN` 配置及脚本中的 Bearer 头。
   - 同步修改 `app/config.py`、`app/dependencies.py`、两个路由文件、`scripts/api_template.py`、README 和上报文档，避免形成“代码已匿名、文档仍称有鉴权”的漂移。
   - 如果希望统一为 `X-Access-Key`，必须先把它改造成不可随意关闭、服务端统一强制执行且适合外部脚本使用的正式鉴权机制，不能直接复用当前手工校验方式。

无论选择哪条路线，都要完成以下动作：

3. 新建 `.env.example`，只保留键名和安全占位符。
4. 从 Git 索引移除 `.env`，但保留本机文件；检查远端历史和仓库可见范围后决定是否清理历史。
5. 若保留 Token，立即生成并部署新值，使仓库中已出现的旧值失效；若移除 Token，则确认所有环境均已部署不依赖该值的新版本。
6. 在 CI 加 secret scanning，阻止 `.env`、Token、QingLong Secret、Bark Key 再次提交。

**验收标准**

- `git ls-files .env` 无输出，`.env.example` 不包含真实值。
- 设计文档明确记录最终采用“应用层机器鉴权”还是“可信网络边界”，并列出部署前提。
- 在任一方案下，3 个写接口都不能被不可信网络匿名调用。
- 若保留 Token：新 Token 生效，旧 Token 请求返回 401；缺少 `INGEST_TOKEN` 时服务拒绝启动，不再接受 `default_token`。
- 若移除 Token：宿主机端口无法绕过代理/ACL 直连，并有自动化或部署检查证明未授权来源无法调用写接口。
- README、脚本模板和库存上报文档准确区分上报凭据、`X-Access-Key` 和青龙 OpenAPI token。
- CI 能拦截测试用的伪泄露 token。

### OPT-002：统一 UI API 的服务端鉴权边界

**现状证据**

- 基线时 `X-Access-Key` 由 `web.py:verify_access_or_raise()` 多处手工调用；本轮已删除重复检查，`web`/`stock` router 统一使用 `require_ui_access()`。
- 受保护 UI API 现在统一接受短时效签名 HttpOnly Cookie；旧 `X-Access-Key` 仅作为一次迁移入口，不再由前端新流程持久化。
- 前端路由守卫只阻止页面导航，无法阻止调用者直接访问 `/api/v1/accounts`、`/programs`、删除接口等。
- 旧版本曾将访问密钥以明文存于 SQLite；现有数据库启动时会将其迁移为带随机盐的 PBKDF2-HMAC-SHA256 哈希并清空旧字段。浏览器新流程不再把原始密钥写入 `localStorage`，但旧版本留下的 `site_access_key` 会在成功迁移后清理。
- `/access/verify` 已增加单进程 IP 失败限流（60 秒 5 次，随后锁定 5 分钟）；访问验证、旧 header 接受、失败和限流事件写入 `access_audit_events`，不记录提交的密钥。

**风险**

- 开启“访问保护”后，若新增路由未挂 `require_ui_access`，仍可能绕过 SPA 直接读取和修改数据，因此新增 UI router 必须显式挂依赖。
- Cookie 会话降低了 XSS/共享浏览器直接读取原始密钥的暴露面；修改密钥会生成新的哈希并使旧签名自然失效。Cookie 被盗后的主动撤销、审计清理策略和多实例限流仍未完善。
- 当前 Docker 单 worker 下，失败尝试会在该实例内统一触发短暂锁定；只有未来启用多 worker 或多实例时，才需要在反向代理补共享限流，否则不同进程可能分别累计失败次数。

**建议方案**

分两步实施：

1. **短期最小闭环**
   - 把访问检查抽到独立依赖，例如 `require_ui_access()`。
   - 在 UI 业务 router 上统一挂依赖，明确豁免 `/access/status`、`/access/verify`、Bearer 上报和静态资源。
   - 所有修改/删除接口必须受保护；读取接口是否允许匿名由配置明确决定，不能依赖“前端看不到”。
   - Axios 响应拦截器统一处理 401：清理会话并跳转访问页。
   - 已增加单进程 IP 维度失败计数和 5 分钟锁定；当前生产单 worker 已满足现有部署形态，未来多 worker/多实例部署再在反向代理补共享限流。

2. **中期会话化**
   - 验证成功后签发短期、可失效的服务端会话；优先 HttpOnly + SameSite Cookie，避免把原始密钥长期放在 localStorage。
   - 数据库只保存密钥哈希，不保存可逆明文；修改密钥时使旧会话失效。
   - 对数据库恢复、删除程序、批量修改 QingLong 定时等高风险操作记录审计日志。

**本轮落地（2026-09-18）**

- `app/dependencies.py` 签发绑定当前 access key 的 8 小时无状态签名会话；Cookie 使用 `HttpOnly`、`SameSite=Lax`，修改 access key 后旧签名自然失效。
- `/access/status` 会把仍携带旧 `X-Access-Key` 的客户端迁移到 Cookie；Vue 登录和设置页不再保存新密钥到 `localStorage`。
- UI API 鉴权收口到 router-level dependency，避免设置、备份和青龙接口的重复校验逻辑漂移；Bearer 上报鉴权不受影响。
- `app/access_control.py` 已增加 60 秒 5 次、随后锁定 5 分钟的单进程 IP 限流，并补充锁定/清除回归测试。
- `system_settings.access_key_hash` 已加入兼容迁移；新密钥只写哈希，旧 plaintext 字段会清空，Cookie 签名绑定哈希而不是原始密钥。
- `access_audit_events` 已加入并在访问验证、旧 header 接受、失败和限流路径落库；审计写入失败不会阻断正常鉴权。
- 当前生产 Docker 为单 worker，暂不要求共享限流；审计后台查询和审计自动清理仍属于长期运维增强项，与本轮测试/工作区代码是否迁移到生产是两件事。
- 已补签名、过期、错误密钥、旧 header 迁移、失败限流、旧库密钥迁移、哈希验证和审计落库回归测试。

**验收标准**

- 保护开启时，不带凭据直接访问任一受保护读写 API 均返回 401/403。
- Bearer 上报不受 UI 会话机制影响。
- 保护关闭时保持现有易用性。
- 密钥不会通过 GET API、日志或错误信息返回。
- 数据库不再持久化新的明文 UI access key；旧库启动迁移后 `system_settings.access_key` 为空，`access_key_hash` 可验证正确密钥且不能验证错误密钥。
- 失败、验证成功和限流事件可在 `access_audit_events` 中追溯，事件不包含提交的 access key。
- 自动化测试覆盖“关闭保护、开启保护、正确凭据、错误凭据、过期会话”五类场景。

### OPT-004：重构 SQLite 数据库恢复流程

**现状证据**

- `web.py` 当前会先把上传文件落到同卷临时文件，执行 SQLite `integrity_check`/核心表校验，关闭当前 session、`engine.dispose()`，再使用同卷 `os.replace()` 替换主数据库文件。
- 应用启用了 WAL；恢复前会执行 `wal_checkpoint(TRUNCATE)`，若 SQLite 返回 busy 则以 503 安全中止，不继续删除 sidecar 或替换文件。
- 当前已增加以数据库路径为粒度的跨进程旁路锁；维护态会拒绝其他 API 请求，Bark/QingLong 通过同一状态探测跳过调度。
- 上传文件限制为默认 256 MiB；回滚副本按时间戳命名并保留主库及存在的 `-wal`/`-shm` sidecar。

**风险**

- 恢复期间仍有连接写入，可能产生不一致、旧 WAL 重放或恢复后连接状态异常。
- 复制中途进程退出会留下半写文件。
- 无限上传可耗尽磁盘。

**建议方案**

1. 引入全局“维护模式/恢复锁”：当前已实现进程内状态 + 跨进程旁路文件锁，开始恢复后拒绝新业务请求、等待当前进程在途请求退出并跳过调度；其他 worker 的在途事务由 checkpoint 闸门兜底。
2. 限制上传大小，校验扩展名、SQLite header、`integrity_check`、核心表和 `schema_version`。
3. 对现库执行 WAL checkpoint，busy 时返回 503；关闭连接池，备份主库及相关 sidecar。
4. 把验证后的数据库复制到目标目录的临时文件，再用同卷 `os.replace()` 原子替换。
5. 明确清理或隔离旧 `-wal` / `-shm`，恢复后重新建连并跑只读 smoke check。
6. 回滚副本按时间戳命名并支持保留策略；UI 明确提示恢复期间不可用和是否需要重启。
7. 更稳妥的部署可将“导入”改为离线管理命令，由运维在停止服务后执行。

**验收标准**

- 恢复中业务请求返回 503/维护提示，不会继续写库。
- 中断替换前，原数据库仍完整可用；成功后新库通过 `integrity_check`。
- WAL 模式下并发写入测试不产生损坏或旧数据回放。
- 超过大小限制的文件在写满磁盘前被拒绝。
- 有自动化测试覆盖有效备份、非 SQLite、缺表、损坏库和恢复回滚。

**本轮落地（2026-09-18）**

- `app/maintenance.py` 增加跨进程数据库旁路锁；同一路径的第二个恢复任务返回 503，其他 API 请求在维护期间返回 503。
- 恢复前检查 `PRAGMA wal_checkpoint(TRUNCATE)` 的 busy 结果；检测到其他 worker 仍占用事务时不删除 sidecar、不替换数据库。
- API、Bark 和 QingLong 的数据库任务进入统一在途计数；维护锁拿到后等待当前进程任务退出，超时则安全返回 503。
- 增加同进程、跨进程锁可见性回归测试；完整真实数据库导入/失败回滚集成测试仍待补齐。

### OPT-006：正式迁移、外键和删除策略

**现状证据**

- `ensure_*_columns()` 在大量请求入口检查表结构，运行时执行 DDL。
- `database.py` 现在已设置 `PRAGMA foreign_keys=ON`，但仍缺少正式迁移器和旧库孤儿数据治理。
- `StockHistory` 没有外键；删除程序时只删除 `PointsHistory` 和 `Product`，不删除 `StockHistory`，会留下孤儿历史。
- `SystemSettings` 逻辑上是单例，但数据库没有强制单行。

**建议方案**

1. 引入 Alembic（或至少自有 `schema_version` + 顺序迁移器），迁移在启动前/部署阶段执行。
2. 从请求热路径移除 schema introspection 和 DDL；保留一段兼容期后删除 lazy migration。
3. SQLite 连接已开启 `PRAGMA foreign_keys=ON`；下一步要在迁移/旧库清理完成后补齐 `StockHistory` 外键和明确级联规则，不能仅依赖连接级开关。
4. 明确级联规则：
   - 删除账号 → 删除其 `PointsHistory`。
   - 删除程序 → 删除 `PointsHistory`、`Product`、对应 `StockHistory`。
   - 商品历史是审计数据还是随程序删除，需在迁移前确认；若保留则增加明确的软删除/归档语义。
5. 为 `SystemSettings` 固定主键或加唯一单例约束。
6. 用旧版本数据库 fixture 验证从每个受支持版本升级到最新。

**验收标准**

- 正常 API 请求不再执行 `ALTER TABLE` 或反射整张表结构。
- 删除实体后无未定义的孤儿行。
- 新库和至少一个旧库样本均能一键迁移；迁移失败不会启动应用。
- 每个迁移有升级验证和备份/回滚说明。

### OPT-007：强化输入、上传和批量限制

**验收标准**

- 空 ID、超长名称、负值、NaN/Infinity、超大数组有稳定错误响应。

### OPT-010：库存中心真实分页与首屏性能

**现状证据**

- `/stock/center` 返回全部可见商品；`StockPage.vue` 收到全部数据后再执行映射、中文排序、筛选，所谓无限加载只是 `filteredProducts.slice(0, visibleCount)`，没有减少数据库查询、网络传输或 JSON 解析量。
- 页面 `onMounted()` 在库存中心完成后，还会自动请求已隐藏列表和**全部**已下架商品；打开对应抽屉时 watcher 又会再次请求，存在无用和重复加载。
- `stockCenterCache` 位于组件实例中，离开 `/stock` 后随组件卸载销毁，因此“60 秒缓存”不能让再次进入页面立即显示。
- `/stock/center` 为每个程序重新扫描一次全部商品来生成 `programs` 汇总，复杂度接近 `程序数 × 商品数`；当前 `StockPage.vue` 并未读取响应中的 `programs` 字段，这部分计算和传输没有实际消费者。
- 路由守卫在缓存过期后会先等待 `/access/status`，首次进入还要加载懒加载路由 chunk；二者是次要串行等待，应在核心数据链路缩小后再优化感知体验。

**当前数据实测基线（2026-09-18，只读测量）**

- 数据库共有 19,513 个商品，其中默认可见 9,248 个、已下架 10,260 个、手动隐藏 5 个。
- 当前 `/stock/center` 等价响应约 3.56 MiB 原始 JSON、0.70 MiB gzip。
- 页面自动加载的已下架响应约 2.97 MiB 原始 JSON、0.60 MiB gzip。
- 一次进入页面会处理约 19,508 个商品对象，合计约 6.53 MiB 原始 JSON、1.30 MiB gzip，尽管首屏只展示 20 条。
- 现有查询计划会扫描可见商品并使用临时 B-tree 排序；最新余额查询缺少 `(program_id, wechat_id, report_time, id)` 组合索引。
- 20 条首屏商品的近似响应仅约 7.1 KiB 原始 JSON、1.3 KiB gzip；与全量响应相比可减少约 99.8% 的传输量。

**第一阶段实测结果（当前工作区）**

- 在同一份本地数据库、ASGI 直连测量中，新的 `/stock/center?page=1&size=20` 返回约 8.2 KiB 原始 JSON、2.5 KiB gzip，接口耗时约 105 ms；仍需在真实局域网/部署设备上做 p95，而不是把本地单次耗时当作最终指标。
- 新的 `/stock/off-shelf?page=1&size=50` 返回 50 个商品（按程序分组显示为最多 20 个分组），约 17.1 KiB 原始 JSON、5.4 KiB gzip，接口耗时约 37 ms；打开抽屉后可继续点击加载下一页。
- 与基线的全量默认进入相比，首屏传输和 JSON 解析不再随 9,248 个可见商品线性增长；下架明细也不再一次性返回 10,260 个商品。

**首屏感知优化已落地（2026-09-18）**

- `App.vue` 增加全局导航进度条和受保护页面骨架，路由守卫、动态 chunk 或接口准备期间不再出现纯白区域。
- `router.js` 保留动态导入，同时在仪表盘空闲、库存菜单 hover/focus 时预加载 `StockPage` chunk；预加载失败会清理 promise，后续导航仍可重试。
- 该优化只改变加载感知和 chunk 时机，不绕过 access-status 检查，也不改变后端鉴权边界。

**条件缓存已落地（2026-09-18）**

- `/api/v1/stock/center` 在 SQLite 上通过 `stock_center_revision` 和商品、积分历史、小程序、库存历史触发器维护精确失效计数；商品/库存/余额/标签等源数据发生增删改时，旧 ETag 自动失效。
- 请求带匹配的 `If-None-Match` 时，在执行库存分页、汇总和标签查询前返回 `304`；200/304 都返回 `ETag` 与 `Cache-Control: private, max-age=0, must-revalidate`。
- 非 SQLite 后端或 revision 初始化失败时使用完整响应摘要生成 ETag，宁可多做一次查询也不返回可能过期的 304。当前 revision 表/触发器仍是兼容旧库的 lazy setup，正式迁移阶段应纳入迁移器。

**建议方案**

1. **建立真实的库存分页契约**
   - `/stock/center`（或兼容期内新增 v2 路由）接受 `page/size/q/tag/status/price_mode/cash_max/sort`。
   - 响应只返回当前页商品，并同时提供 `total`、汇总计数、`available_tags`、`hidden_total`、`off_shelf_total` 和 `revision`。
   - 搜索、标签、库存状态、价格类型、现金上限和“可兑换”筛选移到服务端；前端无限滚动只追加下一页。
   - 删除前端未使用的 `programs` 响应，或将确有用途的程序聚合改为单次 `GROUP BY`。

2. **优化 SQL 与索引**
   - 合并积分/现金最高余额的重复查询，避免扫描两次相同历史范围。
   - 经正式迁移把 `is_hidden/is_unlisted` 回填并约束为非空，使查询使用简单等值条件而不是 `OR ... IS NULL`。
   - 基于 `EXPLAIN QUERY PLAN` 验证后增加组合索引，候选为：
     - `points_history(program_id, wechat_id, report_time DESC, id DESC)`
     - `products(is_hidden, is_unlisted, points, id)`
   - 当前数据只读副本中，前一个索引可把合并后的最新余额查询从几十至上百毫秒量级降低到约 5 ms；正式结果仍须在目标设备和真实 ORM 路径复测。
   - 第一阶段用 `LIMIT/OFFSET` 足够；只有深页性能实测不达标时再改游标分页。

3. **按需加载抽屉数据**
   - 首屏只获取隐藏/下架数量，不获取商品明细。
   - 仅在用户首次打开抽屉时请求明细；已下架接口也必须支持服务端分页与搜索。
   - 避免 `onMounted()` 和 drawer watcher 对同一数据重复请求。

4. **使用可失效的跨页面缓存**
   - 把第一页、汇总和筛选条件移到独立 store/module，使缓存跨组件卸载继续存在；不要把几千条完整数据同步写入 `localStorage`。
   - 页面再次进入时先展示缓存，再后台静默刷新（stale-while-revalidate），不要先清空为白屏。
   - 每次积分上报、库存上报、隐藏/恢复/重新上架时更新统一的 `inventory_view_revision`；缓存、ETag 和前端状态据此失效。

5. **缩短路由阶段的感知等待（本轮已落地，后续做度量）**
   - 已在登录后的仪表盘空闲和库存菜单 hover/focus 时预加载 `StockPage` chunk，并保留失败重试。
   - 已给 router-view 增加全局导航骨架/进度反馈，使组件 chunk 和路由守卫等待期间不出现纯白区域。
   - 后续用浏览器 Performance/Network 记录冷进入、热进入、慢鉴权和弱网四种场景，确认预加载没有把首屏资源竞争推高。
   - 完成 OPT-002 的服务端统一鉴权后，再把 `/access/status` 从每次过期后的阻塞式路由检查改为后台复验 + 全局 401 处理，不能以降低白屏为由先削弱鉴权。

6. **控制长时间滚动后的 DOM 数量**
   - 首屏问题由服务端分页解决；当用户连续加载很多页时，再引入虚拟网格，只渲染视口附近商品卡。
   - 保留现有 `shallowRef`，避免重新引入大数组深层响应式开销。

`/programs` 当前只有约 222 条记录，其 Python 全量排序不是库存白屏主因；程序列表服务端分页仍应做，但优先级低于库存中心链路，可在本项后半段或独立 PR 处理。搜索所需拼音可在程序更新时缓存 `name_pinyin/name_initials`。

**验收标准**

- 首次进入库存页不再请求全部在架或全部下架商品；首屏商品接口最多返回约定页大小（默认 20）。
- 默认首屏压缩响应建议控制在 20 KiB 内；不得随商品总量线性增长。
- 重复进入页面可立即展示未过期或可后台复验的第一页缓存，不出现空白内容区。
- 局域网目标环境首批商品 p95 建议不高于 300 ms，远程常规网络建议不高于 800 ms；最终阈值以部署硬件和链路基准确认。
- 隐藏/下架抽屉只在打开后加载，支持分页，并且相同操作不会触发重复请求。
- 常规分页 SQL 只读取当前页和必要聚合；`EXPLAIN QUERY PLAN` 不再对默认首屏执行无索引的全表排序。
- 搜索、标签、价格、库存、可兑换筛选和原有排序都有新旧语义对照测试。
- 使用浏览器 Network/Performance 面板记录冷进入、热进入、筛选和连续下拉四条基线，PR 中附改造前后数据。

### OPT-011：修正同步 I/O、路由并发与后台任务生命周期

**现状证据**

- `web.py` 大部分 endpoint 声明为 `async def`，内部却使用同步 SQLAlchemy、`requests`、sqlite3、shutil；这些调用会直接阻塞 event loop。
- `images.py` 在 async route 中同步复制上传文件。
- Bark/QingLong 使用 daemon thread + `time.sleep()`，没有显式 shutdown、stop event 或锁释放流程。
- 启动使用已逐步弃用的 `@app.on_event("startup")` 模式。

**建议方案**

- 短期：纯同步 SQLAlchemy/文件 I/O 路由改为普通 `def`，让 FastAPI 在线程池执行；真正 async 的上传分块使用 await，重 CPU/文件操作显式 offload。
- 中期二选一：保持完整同步栈，或整体迁移 async SQLAlchemy + `httpx.AsyncClient`；不要半同步半异步。
- 使用 FastAPI lifespan 管理 scheduler 启停、stop event、线程 join、HTTP client 和文件锁。
- 对外部 QingLong/Bark 调用配置连接复用、超时、有限重试和退避；重试仅用于幂等操作。
- 避免 blocking QingLong 同步占用列表请求；默认保持后台同步，UI 展示“数据时间/同步中”。

**验收标准**

- 慢 QingLong/Bark 请求不会卡住无关 API。
- 应用关闭时后台线程能在有限时间内退出并释放锁。
- 并发 smoke test 下没有 event-loop 长时间阻塞告警。

**第一阶段实施记录（2026-09-18）**

- 大部分同步数据库/文件/网络 I/O 路由已改为普通 `def`，交给 FastAPI 线程池执行。
- FastAPI 已改用 lifespan；Bark/QingLong 调度器使用 `threading.Event` 停止、有限时间 join，并在成功退出后释放进程锁。
- Bark 已按线程复用 `requests.Session` 连接池，保留 15 秒超时和响应校验；关闭自动重试，避免通知类请求重复发送，并在 scheduler/shutdown 时释放连接池。
- QingLong `get_token`、`list_crons` 和 `update_cron_schedule` 已按调用线程复用带连接池的 `requests.Session`，保留 15/30/20 秒超时；scheduler/shutdown 会释放连接池，手动同步可在关闭后按需重建。
- QingLong HTTP adapter 明确设置 `max_retries=0`；尤其不对修改任务的 PUT 自动重试，避免网络超时后产生重复更新。未来若增加重试，只允许明确幂等的 GET，并先补退避和并发基准。

- 增加自动备份、保留和恢复演练，而不只提供手工下载按钮。

**验收标准**

- 新机器只需环境变量和持久化卷即可启动，不要求宿主机安装 Node。
- 容器进程不是 root；代码目录运行时只读。

### OPT-015：统一请求、缓存、响应式断点和错误处理

**现状证据**

- `PointsPage.vue:436` 的 `computed(() => window.innerWidth...)` 没有响应式依赖，窗口变化后抽屉尺寸不会可靠更新。
- 多个页面各自注册 resize/IntersectionObserver、格式化错误信息和 401 行为。
- Programs 页面把整页程序数据写进 sessionStorage，没有 TTL/版本；访问身份或后端数据变化后可能展示陈旧数据。

**建议方案**

- 用一个响应式 `useViewport()` 提供断点，统一注册/移除监听。
- Axios 层统一：401 会话失效、错误格式、request ID、超时分类、可取消请求。
- 搜索和筛选请求使用 debounce + AbortController，避免旧响应覆盖新状态。
- 页面状态缓存只保存筛选条件和滚动位置；如缓存数据，必须带 schema version、账号/session 标识、后端更新时间与 TTL。
- 对有副作用按钮统一 pending 防重复、成功后局部更新或可控重载。
- 为键盘操作、焦点回收、dialog/drawer、颜色对比度补基础可访问性检查。

**本轮落地（2026-09-18）**

- 增加 `frontend/src/composables/useViewport.js`，统一封装响应式视口宽度和 `resize` 监听；`QinglongCronsPage.vue` 与 `PointsPage.vue` 已迁移，积分抽屉不再直接读取不可响应的 `window.innerWidth`。
- 增加 `frontend/src/composables/useAccessSession.js`，把旧版 localStorage 会话迁移清理从 API、路由和页面中收口，避免多个入口各自实现鉴权兼容逻辑。

- 开启访问保护后，服务端 API 无绕过路径。

顺序：OPT-004 → OPT-006 → OPT-007 → OPT-008。

完成标准：

- 数据库恢复有维护锁、原子替换和 WAL 测试。

顺序：先记录库存页冷/热加载基准，再优先做 OPT-010；随后完成 OPT-009 的其余历史查询优化，再做 OPT-011。OPT-010 所需的两条针对性索引随库存分页 PR 一并迁移，不必等待 OPT-009 全部完成。

完成标准：

- 常用列表不扫描全部历史/商品。
- 库存首屏使用真实服务端分页，进入页面不再自动下载全部下架商品，重复进入可先显示跨页面缓存。
- 慢外部服务不会阻塞无关请求；后台线程可优雅退出。

### 阶段 D：部署与可观测性

实施 OPT-012、OPT-013。

完成标准：

- 有 live/ready、结构化日志、审计和最小告警。

## 11. 暂不建议的做法

- 在没有测试和迁移基线前一次性重写后端或改用另一套数据库。
- 只在前端隐藏按钮来“保护”写接口。
- 为解决 SQLite 锁问题盲目增加 uvicorn workers。
- 继续把新列靠请求时 `ALTER TABLE` 长期维护。
- 为性能先引入缓存层，却不先确认最慢 SQL 和全量加载点。
- 在库存全量快照语义未加完整性信号前，简单取消所有下架检测；这会重新引入失效商品长期残留。
- 把真实备份库、日志、上传图片或密钥加入测试 fixture/仓库。
